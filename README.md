# AD Robot

Обёртка над Keitaro Admin API. Создаёт кампанию с двумя потоками из трёх полей и
редактирует офферы внутри потока — с тем же пересчётом долей, что и в эталонном
инструменте. Тестовое задание для Eto Legko.

Бэкенд — FastAPI + SQLAlchemy 2.0 + PostgreSQL, фронт — React + TypeScript + Vite.

## Запуск

Нужны Docker с compose v2 и `make`. Больше ничего: Python и Node живут внутри образов.

```sh
git clone git@github.com:firstConsole/test-task-adrobot.git
cd test-task-adrobot
cp .env.example .env
make up
```

Интерфейс — <http://localhost:8080>.

`make up` — это `docker compose up -d --wait --build`: собрать образы, поднять Postgres,
**прогнать миграции** и дождаться, пока API ответит на `/healthz`.

| | Адрес |
|---|---|
| Интерфейс | <http://localhost:8080> |
| API | <http://localhost:8000/api/v1> |
| Swagger | <http://localhost:8000/docs> — только при `ADROBOT_ENV=dev` |
| Живость, готовность | <http://localhost:8000/healthz>, <http://localhost:8000/readyz> |

Всё публикуется на `127.0.0.1`, наружу не торчит ничего. `make down` — остановить, база
переживёт в томе `pgdata`; `docker compose down -v` — снести вместе с базой.

### Что подставить в `.env`

`.env.example` — рабочий файл, а не список имён: со значениями как есть стек поднимается
и интерфейс открывается. Ненастоящего в нём два сорта, и оба видно глазами:

```sh
grep -n 'replace-me\|tracker.invalid' .env
```

- **`ADROBOT_KEITARO_BASE_URL`** и **`ADROBOT_KEITARO_PUBLIC_BASE_URL`** — адрес трекера
  с префиксом `/admin_api/v1` и без него. По умолчанию это `tracker.invalid`: TLD, который
  по RFC 2606 не резолвится никогда — чтобы недонастроенный стек физически не смог
  отправить `Api-Key` на чужой хост.
- **`ADROBOT_KEITARO_API_KEY`** — ключ Admin API. Держится как `SecretStr`, разворачивается
  ровно в одном модуле и уходит в заголовке `Api-Key` тому хосту, который назван выше.

Пока они не заменены, работает всё, что не ходит в трекер: список кампаний, зеркало
потоков, черновик и пересчёт долей. `PUSH TO KT` — нет.

**`ADROBOT_ACCESS_TOKEN`** — общий токен на изменяющих ручках нашего API. В браузере его
никто не вводит: токен держит прокси — nginx в compose, dev-сервер Vite локально — и
подставляет `Authorization: Bearer` в каждый запрос к `/api`. В бандл он не попадает.
Заменить его нужно до того, как сервис станет виден не с localhost.

### Миграции

Alembic поверх асинхронного движка; ревизии пронумерованы руками — `0001` … `0004`,
а не хешами, чтобы порядок читался из имени файла.

- **После `make up` они уже применены.** Их применяет одноразовый сервис `migrator`
  (`alembic upgrade head`) на том же образе, что и API, а API стартует только после его
  успешного выхода. В lifespan приложения миграций нет намеренно: несколько воркеров
  начали бы гонку друг с другом.
- На уже поднятом стеке — `make migrate`.
- Новая ревизия — `make revision REV=0005 M="..."`, оба аргумента обязательны.
  Автогенерация предлагает, а не решает: файл читается перед коммитом, а
  `alembic upgrade head --sql` печатает SQL, ничего не выполняя.

### Локально, без Docker

Понадобится для тестов и линтеров: Python 3.13 с Poetry и Node 26 (`frontend/.nvmrc`).

```sh
make install                             # зависимости бэкенда
make test                                # весь набор
make lint typecheck imports              # ruff, mypy strict, границы слоёв
cd frontend && npm ci && npm run dev     # фронт на :5173, /api уходит на :8000
```

Тесты, которым нужен Postgres, подхватывают тот, что поднял `make up`, и снимаются с
внятной причиной, если его нет: на свежем клоне `make test` зелёный. `make help` —
остальные цели.

Сам сервис руками запускать не нужно, но если очень надо: настройки читаются только из
окружения, `.env` лежит в корне, а все бэкендовые команды выполняются из `backend/` —
поэтому `set -a; . .env; set +a` и потом уже `uvicorn`.

### Проверка на чистой машине

```sh
scripts/verify-fresh.sh
```

Клонирует HEAD во временную папку, выполняет там ровно то, что обещано выше — `cp
.env.example .env` и `docker compose up`, — и спрашивает поднявшийся стек: отвечают ли
health-ручки, даёт ли API 401 без токена и 200 с ним, доведён ли alembic до головы, на
месте ли восемь таблиц, отдаёт ли nginx собранный SPA и проксирует ли он `/api`. Потом
убирает за собой. Проверяется **HEAD, а не рабочее дерево**: незакоммиченного у ревьюера
не будет. Занятые порты — повод отказаться, а не поднять второй стек поверх вашего.

Тот же скрипт крутится в CI джобой `compose-smoke`, так что обещание «четыре команды»
проверяется на каждом PR, а не на слово.

## Демо

Сквозной сценарий: кампания создаётся из трёх полей, открывается в редакторе, получает и
теряет оффер, уезжает в трекер.

![Сквозной сценарий: создание кампании, правка потока, PUSH TO KT](docs/media/demo.gif)

**Создание кампании.** Три поля — имя, гео из списка ISO 3166-1 и оффер через тот же
автокомплит, что и в редакторе. Предупреждение внизу срабатывает на **пересечении** гео
оффера с гео кампании: Flow 1 забирает названную страну себе, так что до оффера она не
доедет.

![Экран создания кампании](docs/media/create-campaign.png)

**Список кампаний.** Импорт существующей по её id в Keitaro — так открывается кампания,
которую этот сервис не создавал. `FINISH SETUP` появляется у кампании, чьи потоки трекер
не принял: она есть, названа и её можно дошить.

![Список кампаний с формой импорта](docs/media/campaign-list.png)

**Редактор, чистое состояние.** Flow 1 — редирект по гео, у него нет таблицы офферов и
виджета добавления. Flow 2 крутит офферы: доли показаны ровно те, что лежат в трекере, и
если они дают в сумме не 100 — так и нарисовано. Кнопки `PUSH TO KT` нет, потому что нечего
пушить.

![Редактор потоков, чистое состояние](docs/media/stream-editor-clean.png)

**Редактор, черновик.** Добавленная строка, вычеркнутая с `BRING BACK`, закреплённая доля,
и сводка «что уедет» — `34 → 33` по каждой изменившейся строке. Остаток от деления у
последней активированной строки; сумма активных — 100.

![Редактор потоков с грязным черновиком](docs/media/stream-editor-dirty.png)

## Как считаются доли

ТЗ называет один критерий качества явно: «главное, чтобы кнопки работали и цифры были
верные». Цифры — вот эти.

**Правило целиком:**

1. закреплённая (pinned) строка держит ту долю, на которой её закрепили;
2. удалённая строка получает 0 и в дележе не участвует;
3. остаток от 100 делится нацело между свободными активными строками — `divmod`;
4. `extra` единиц раздаются по одной, начиная с **последней активированной** строки:
   последнее добавление, последний `BRING BACK`, а для строк, приехавших из трекера, —
   по убыванию `created_at`.

Везде целые числа: `round()` и float — ровно то, из-за чего на экране появляется 99%.

### Четыре состояния из видео

Сняты покадрово с записи эталонного инструмента и служат спецификацией. В коде это
именованные фикстуры в [`backend/tests/domain/test_shares.py`](backend/tests/domain/test_shares.py),
таймкод — часть имени.

| Состояние | 3749 | 3717 | 11111 | 11112 |
|---|---|---|---|---|
| `t=0` — три оффера, как их отдал трекер | 33 | 33 | **34** | — |
| `t=124` — добавлен четвёртый | 25 | 25 | 25 | 25 |
| `t=208` — 3717 удалён, остаётся серой строкой | 33 | 0 | 33 | **34** |
| `t=328` — 3717 закреплён на 25, 11111 удалён, 3749 возвращён | **38** | 25 | 0 | 37 |

Жирным — строка, которой достался остаток от деления. Пункт 4 правила — единственный,
который не выводится из здравого смысла, и именно он решается этой таблицей:

- **«остаток первому по порядку вставки»** (`seq ASC`) — правило, которое напрашивается
  первым, — ошибается в двух состояниях из четырёх: в первом отдаёт 34 офферу 3749 вместо
  11111, в третьем — ему же вместо 11112;
- **«остаток последнему по порядку вставки»** (`seq DESC`) проходит первые три состояния
  и ломается на четвёртом: остаток должен получить возвращённый 3749 — самая старая строка
  потока, — а не более поздний 11112.

Множество значений при этом совпадает во всех трёх вариантах (33/33/34), так что тест,
утверждающий кортеж, неверное правило пропускает. Поэтому тесты утверждают **словарь**
`оффер → доля`: ревьюер сверяет именно пары, открыв поток в Keitaro.

**Порядок на экране — отдельное правило, не путать с раздачей остатка:** активные по
убыванию доли, при равенстве — по порядку вставки, удалённые в конце. Из-за этой сортировки
получатель остатка всегда всплывает наверх, и на экране разница между правилами не видна.
В трекере — видна.

### Два поведения, которые выглядят как баг

**Пин ничего не пересчитывает и не делает черновик грязным.** На `t≈318` в эталоне чистое
состояние: две активные строки по 25% (в сумме 50), кнопки `PUSH` нет. Пин решает только,
что произойдёт при следующей правке. Отсюда архитектурное следствие: пин живёт в зеркале
(таблица `offer_pins`), а не в черновике — иначе он не пережил бы `PUSH` и `CANCEL`,
а в эталоне переживает.

**Состояние, прочитанное из Keitaro, не нормализуется.** Сумма долей чистого потока может
быть 50% — это не поломка, а то, что лежит в трекере. Нормализовать её при чтении значило
бы показать цифры, которых там нет; 100% появляется после первой мутации, которая и
запускает пересчёт.

### Где это живёт

[`backend/src/adrobot/domain/shares.py`](backend/src/adrobot/domain/shares.py) — **единственное
место, где вычисляется доля**. Ни в роутере, ни в сценарии, ни на фронте. Модуль импортирует
только stdlib, и это проверяет `import-linter` в CI.

В API намеренно нет ручки, принимающей строки с готовыми долями: клиент говорит
`add`, `remove`, `bring back` — но не «эти строки держат 34, 33 и 33». Единственное число,
на которое он влияет, — пин, и оно валидируется той же функцией, что делит остальное.
Фронт следует той же границе: **оптимизм в структуре, пессимизм в числах** — вычеркнутая
строка гаснет мгновенно, а доля в ячейке становится скелетоном, пока сервер не ответит.

Чем это держится:

- четыре состояния выше — как тесты на словарь;
- свойства на hypothesis: активные строки делят ровно 100, когда есть хоть одна свободная;
  пин держит в точности своё значение; удалённая строка равна нулю и не влияет на остальных;
  пересчёт идемпотентен; результат не зависит от порядка поступления строк; добавление
  строки никому не повышает долю; каждая доля — целое в `[0, 100]`;
- `make cov` держит два порога: **100% на `domain/shares.py`** и 90% на `domain/` вместе
  с `application/`.

## Архитектура

### Три кольца

```
domain/            только stdlib: доли, черновик, кампания, гео
    ↑
application/       порты (ABC) и сценарии; знает domain, не знает FastAPI и SQLAlchemy
    ↑
infrastructure/    ←→    api/        независимые соседи, оба знают application
    ↑
composition.py, main.py              единственные модули, которые видят всё
```

Четыре пакета, а не пять: никаких `interfaces/`, `adapters/`, `presentation/` поверх.
Главное здесь не схема, а то, что границы **проверяются, а не декларируются** —
три контракта `import-linter` отдельным job в CI:

1. `domain/` не импортирует ничего, кроме stdlib. Контракт запрещает всё и выдаёт
   поимённый список разрешённых модулей стандартной библиотеки — так зависимость,
   добавленная через три этапа, ловится в день, когда доедет до домена.
2. `application/` не импортирует ни `infrastructure`, ни `api`, **включая косвенные рёбра**:
   сценарий, дотянувшийся до `composition.py`, дотянулся через него до инфраструктуры, и
   контракт падает и на этом.
3. Проводные модели Keitaro (`Kt*`) импортирует только `mapping.py`. Это формат чужого
   API, а не наш тип; конвертация — в одном модуле.

### Контейнеры

```
браузер ──▶ web (nginx, :8080) ──/api/──▶ api (uvicorn, :8000) ──▶ db (postgres, :5432)
              отдаёт SPA,                      │
              держит общий токен               └── HTTPS, Api-Key ──▶ Keitaro Admin API
```

Плюс `migrator` — одноразовый контейнер на том же образе, что и `api`.

### Данные: зеркало, черновик, пины

Восемь таблиц тремя группами, и группа решает, насколько строгой быть схеме.

**Зеркало** (`campaigns`, `streams`, `stream_offers`, `offers`) — то, что прочитано у
трекера. Терпимое: `text`, `text[]`, без CHECK. Внешнего ключа
`stream_offers.offer_id → offers.id` нет — оффер может оказаться в потоке раньше, чем в
нашем каталоге, и неизвестный оффер рисуется как `#11234`, а не роняет синхронизацию.
Обновление зеркала после пуша ставит tombstone, а не удаляет строку.

**Черновик** (`stream_drafts`, `stream_draft_rows`, `push_attempts`) — наше, строгое. Один
открытый черновик на поток держит частичный уникальный индекс, а не блокировка в коде.

**Пины** (`offer_pins`) — в зеркале, а не в черновике, см. раздел о долях.

Экран редактора — это **зеркало ⊕ черновик ⊕ пины**, собранные в одном месте
(`application/use_cases/editor.py`). Всё, что пишет, отвечает тем же `StreamEditorView`,
поэтому «порядок строк после добавления» и «порядок строк после перезагрузки» — одно
правило, а не два.

CHECK «сумма долей = 100» нет намеренно: он ложен и для зеркала (у трекера бывает 50),
и для черновика, в котором закреплены все строки.

### PUSH TO KT — три фазы

```mermaid
sequenceDiagram
    participant UI as Браузер
    participant API as api
    participant DB as Postgres
    participant KT as Keitaro

    UI->>API: POST …/draft/push
    Note over API,DB: фаза 1 — короткая транзакция
    API->>DB: что писать; push_attempt = in_flight, draft = pushing
    Note over API,KT: фаза 2 — транзакции нет, здесь могут пройти секунды
    API->>KT: PUT /streams/:id — желаемое состояние целиком
    KT-->>API: 200
    API->>KT: GET — перечитать поток и сравнить с записанным
    Note over API,DB: фаза 3 — короткая транзакция
    API->>DB: зеркало, черновик закрыт, аудит закрыт
    API-->>UI: поток целиком, уже пересчитанный
```

- **Транзакция БД никогда не открыта поверх HTTP-вызова.** Соблазнительная версия
  (`async with uow.begin(): await admin.push(...)`) выедает пул соединений в первую же
  минуту, когда Keitaro задумался.
- **Отправляется желаемое состояние целиком, а не дельта.** Удалённые строки уезжают явно
  как `{offer_id, share: 0, state: "disabled"}` — это корректно и при replace-, и при
  merge-семантике массива. Строка, просто не попавшая в payload, на мержащем билде
  продолжила бы получать трафик, а сумма долей уехала бы за 100.
- **Перед записью — чтение.** Черновик помнит отпечаток потока, на котором открыт; фаза 2
  читает поток из трекера и сравнивает. Уехавший поток означает, что кампанию правили
  руками, и push останавливается с 409, показывая оба состояния. Сравнение — с **трекером**,
  а не с нашим зеркалом: устаревшее зеркало ничья не вина, а перезаписать собираются
  трекер. Rebase нет: проигрывание журнала поверх чужой правки даёт третье состояние,
  которого не просил никто. Два честных ответа — перезаписать осознанно (`overwrite`) или
  выбросить черновик.
- **Неудачный push — событие, а не состояние.** Черновик возвращается в `open` ровно с теми
  же строками, а `push_attempts` записывает, какого рода был отказ. Отдельно стоит
  `indeterminate`: запрос ушёл, ответ не пришёл — выход отсюда чтение, а не слепой ретрай.
  Создающий POST не ретраится никогда.
- **Пересчёта на пуше нет.** Уезжает ровно то, что показывал экран: пересчёт, которого никто
  не видел, — это и есть «цифры разошлись с трекером».

### Часть 1: три записи в чужую систему без транзакции вокруг них

Кампания, затем два потока. Вопрос, на который отвечает дизайн, — что остаётся у человека,
когда падает вторая или третья.

**Ничего не откатывается.** Удалять кампанию, которая в трекере уже есть, по слову
падающего запроса — единственный исход, который с экрана не отменить. Вместо этого локальная
строка пишется в момент, когда кампания появилась, помечается `needs_attention` и несёт
запрошенные гео и оффер. Дошивает её кнопка `FINISH SETUP` (`POST /campaigns/{id}/repair`) —
и это тот же код, которым строится каждая кампания, а не аварийная ветка, которая гниёт
между инцидентами.

Группа, источник и домен читаются из API трекера (кэш пять минут), а не из окружения: ТЗ
прямо говорит, что «всё это тоже есть в API». Группы кампаний нет — создаётся один раз, под
локом, чтобы два одновременных запроса не завели две одноимённые.

Потоки называются `Flow 1` и `Flow 2`, как в эталонной кампании. Flow 1 — `schema: redirect`,
фильтр `country = <гео кампании>`, увозит на `https://google.com`. Flow 2 — `schema: landings`,
забирает всё остальное и крутит офферы; это и есть поток, который редактирует часть 2.

**Следствие, которое легко прочитать наоборот:** названная в форме страна — единственная,
которая до оффера **не доедет**. Поэтому предупреждение на экране создания срабатывает на
**пересечении** гео оффера с гео кампании, а не на их несовпадении: MX-оффер в MX-кампании
не увидит ни одного мексиканского клика.

### Фронт

FSD-lite: `app / pages / widgets / features / entities / shared`. Widgets ровно один —
`stream-group`, настоящая композиция. `features/` содержит **только мутации**; чтение и
отображение бизнес-объекта живёт в `entities/` — иначе автокомплит офферов, нужный на обоих
экранах, стал бы импортом feature → feature.

Границы держит `eslint-plugin-boundaries`: слой ходит только в разрешённые слои, а в слайс
входят через его `index.ts`, а не файл за файлом. Единственный кэш — TanStack Query;
глобального стора нет.

Два файла фронта сгенерированы и руками не правятся: типы API — из
`docs/adrobot-openapi.json`, список стран — из `domain/geo.py`. CI перегенерирует оба и
падает на любом расхождении, так что «поправил руками» живёт до следующего `make`.

## Решения и допущения

Каждая строка — развилка, на которой был выбор, и цена выбора.

- **Класс заводится там, где есть состояние с инвариантом или вторая реализация**, и больше
  нигде. Оправданы три: порты Keitaro с HTTP-адаптером (живой клиент и тестовый фейк),
  Unit of Work с репозиториями, агрегат `StreamDraft`. Расчёт долей — чистая функция
  `redistribute(rows) -> rows`, а не `ShareCalculatorStrategyFactory`.
- **Портов к трекеру два**, `KeitaroAdminPort` и `KeitaroReportsPort`: чтобы отказ
  `/report/build` гасил колонку статистики, а не редактор целиком.
- **Каталог офферов зеркалится локально**, потому что у `GET /offers` в Admin API **ноль**
  query-параметров — ни поиска, ни пагинации. Автокомплит ищет по локальной копии
  (`pg_trgm` по имени, префикс по id); `POST /offers/sync` перечитывает список. На свежей
  базе копии ещё нет, поэтому пустой выпадающий список так и говорит — «Каталог пуст: из
  Keitaro ещё ничего не читали», а не «Ничего не нашлось», — и предлагает `FETCH OFFERS
  FROM KT` прямо в себе: это два разных положения дел, и кнопкой чинится только одно.
- **Интерфейс — на русском, кнопки-команды — нет.** `PUSH TO KT`, `BRING BACK`,
  `FETCH STREAMS FROM KT` и прочие надписи — это цитаты с кнопок эталонного инструмента, с
  которым ревьюер сверяет экран; переведённая кнопка стоит ему лишней сверки. По той же
  причине не переводятся слова самого Keitaro там, где они данные: `Flow 2`, `stream_id`,
  `disabled`. Тексты отказов приходят с сервера как есть, по-английски: перевод на клиенте
  означал бы таблицу сообщений, которая тихо расходится с API.
- **Авторизация — один общий токен** на изменяющих ручках, bearer-заголовком. Ни таблицы
  пользователей, ни JWT: актор один, а `alg` в заголовке — класс уязвимостей, который просто
  не приезжает, если токен сравнивают, а не разбирают. Зависимость объявлена через
  `Security`, поэтому каждая защищённая операция несёт `security` в OpenAPI —
  `test_no_endpoint_escaped_authentication` читает документ и падает, если ручка ускользнула.
- **Ошибки — RFC 9457** (`application/problem+json`) с `correlation_id`. Таблица
  «исключение → статус» лежит в одном модуле обработчиков: `status` на самом исключении
  заставил бы `domain/` знать, что он стоит за HTTP. Деталь 5xx вне `dev` заменяется
  корреляционным id — 4xx описывает запрос вызывающего, 5xx описывает наши внутренности.
- **Ключ трекера разворачивается ровно в одном модуле.** Текстовый тест держит список
  модулей, которым вообще разрешено называть `keitaro_api_key`. `follow_redirects=False`:
  на кросс-доменном редиректе httpx снимает только `Authorization`, а кастомный `Api-Key`
  унесло бы на новый хост. `httpx.Headers.__repr__` прячет три заголовка, и `Api-Key` не из
  них — поэтому в `transport.py` объект запроса не логируется и не связывается с именем.
- **Проксирующей ручки `/api/kt/{path}` нет и не будет.** Она превращает наш общий токен в
  ключ от чужого трекера.
- **Часовой пояс спрашивается у трекера** (`GET /settings`), лениво и один раз;
  `ADROBOT_KEITARO_TIMEZONE` — то, что стоит, если трекер не ответил или назвал зону,
  которой нет в tz-базе. Keitaro сериализует время без смещения, так что разбор наивной
  метки как UTC сдвигает границу суток на часы — это «цифры неверные», которое переживает
  ревью. Поэтому зона подписана рядом с «clicks today».
- **Статистика деградирует, а не падает.** Окно кэша 45 секунд и три честных состояния:
  сегодняшние числа, последние прочитанные с пометкой времени, либо ничего с той же
  пометкой. Устаревшая цифра с датой полезнее пустой ячейки.
- **`/readyz` не ходит в Keitaro.** Недоступный трекер не делает наш сервис неготовым:
  зеркало, черновик и пересчёт долей работают без него.
- **Alias кампании** генерируется фиксированной длиной из безопасного алфавита
  (`abcdefghijkmnpqrstuvwxyz23456789`, без похожих символов). Фильтрация `token_urlsafe(8)`
  до `[a-z0-9]` примерно в трети случаев даёт меньше шести символов — это плавающая 500-я на
  самой первой кнопке. Alias **чужой** кампании при импорте — просто строка: наши правила не
  повод не открыть кампанию 93212 из видео.
- **`preview_url` собирается на сервере**: трекер отдаёт `preview_path` относительным
  (`/preview/11111`), и склеить его с публичной базой — не работа фронта.
- **Flow 1 не получает виджет добавления офферов.** У него `schema: redirect`; массив
  `offers[]` трекер на нём проигнорирует, а неаккуратный `PUT` затёр бы сам редирект.
  Группа с заголовком рисуется, таблица офферов — только при `schema == "landings"`.
- **На проводе snake_case**, без alias-генераторов: фронт получает типы из OpenAPI, и
  camelCase просто не собрался бы.
- **Асинхронность — ради исходящего HTTP, а не ради базы.** Экрану редактора нужны потоки,
  каталог и отчёт; последовательно это секунды, через `gather` — сотни миллисекунд.
  Отсюда четыре настройки, без которых async SQLAlchemy кусается: `lazy="raise_on_sql"` на
  каждой связи, `expire_on_commit=False`, сессия на запрос и правило про транзакцию поверх
  HTTP. Драйвер `asyncpg`; если перед базой появится pgbouncer в transaction mode,
  понадобится `statement_cache_size=0` либо переход на psycopg3.

**Допущения, которые стоит назвать вслух:**

- **Правило раздачи остатка выведено из видео, а не из документации.** Четырёх состояний
  хватает, чтобы отсечь два конкурирующих правила, но это индукция по четырём точкам. Если
  эталон разойдётся с нами на пятом состоянии, менять придётся одну функцию и её тесты.
- **Арендатор один** — AD Robot внутренний инструмент одной команды. На этом стоят и общий
  токен, и отсутствие RLS (ниже).
- **Трекер — источник правды.** Наши таблицы зеркало, и в любом споре прав он: поэтому
  `PUSH` сравнивает черновик с трекером, а `FETCH STREAMS FROM KT` всегда доступен.
- **Разведка API делалась на конкретном билде Keitaro** — всё, что проверено запросом, а не
  спекой, лежит в [`docs/keitaro-api-notes.md`](docs/keitaro-api-notes.md) с пометкой, чем
  именно подтверждено. Утверждения о спеке продублированы тестами в
  `backend/tests/test_keitaro_spec.py`: если Keitaro починит расхождение, мы узнаем об этом
  красным билдом.

## Чего здесь нет и почему

Список короткий и честный: он отличает «не успел» от «решил».

### PostgreSQL RLS

RLS решает задачу «несколько арендаторов в одной таблице, и приложение не должно иметь
возможности ошибиться». Здесь арендатор один, защищать нечего, а цена вполне реальная:

- контекст арендатора ставится через `SET LOCAL` в каждой транзакции — то есть плюс
  раунд-трип к каждому запросу, а `SET` нельзя параметризовать, значит нужен отдельный
  безопасный путь подстановки;
- сессионные GUC живут на **соединении**, а не на сессии SQLAlchemy: при пуле незакрытый
  контекст утекает в следующий запрос — это не гипотеза, а типовой инцидент;
- для настоящей изоляции нужна отдельная роль без `BYPASSRLS` и не владелец таблиц, то есть
  вторая DSN и пароль, который надо прокинуть ещё и в Alembic.

**Условие, при котором RLS включается:** в этой базе появляется второй арендатор — вторая
команда или внешний клиент. До тех пор изоляцию держат вещи дешевле: `extra="forbid"` на
всех входных схемах, отсутствие клиентски задаваемых долей и авторизация на изменяющих
ручках.

**Отдельные роли БД** (`adrobot_owner` / `adrobot_app`) — по той же причине. Написать такую
миграцию правильно нужно уметь (`ALTER DEFAULT PRIVILEGES` до создания таблиц, `REVOKE` в
той же миграции, что создаёт таблицу), но на однопользовательском инструменте выгода
символическая.

### Celery, RabbitMQ и вообще очередь

В ТЗ очереди нет, и брокер ради брокера — это плюс контейнер, плюс воркер, плюс таблица
задач, плюс вторая страница интерфейса, где смотрят статус задачи.

**Что уехало бы в очередь первым, когда она появится:**

1. **Синхронизация каталога офферов.** Сейчас это кнопка и ручка `POST /offers/sync`,
   потому что `GET /offers` отдаёт список целиком и другого способа его прочитать нет.
   Каталог на десятки тысяч офферов перестанет укладываться в HTTP-запрос — это первый
   кандидат на периодическую задачу.
2. **Ретраи пуша в состоянии `indeterminate`** — запрос ушёл, ответ не пришёл. Сейчас
   выход — перечитать поток руками (`FETCH STREAMS FROM KT`); фоновой задаче это идёт
   лучше, чем интерфейсу.
3. **Прогрев статистики** для списка кампаний, чтобы `/report/build` не дёргался на каждом
   открытии экрана.

**А `PUSH TO KT` очередью не становится, и это не про объём.** Человек стоит перед экраном
и ждёт ответа на один вопрос: записалось или нет. Асинхронный пуш меняет понятный отказ на
идентификатор задачи, за статусом которой надо ходить, — и вся история про конфликт 409,
который надо показать рядом с расхождением, превращается во вторую очередь уведомлений.
Синхронный запрос с таймаутом, аудитом в `push_attempts` и честным `indeterminate`
рассказывает больше.

### Остальное — списком

- **Таблица `idempotency_keys` и обязательный `Idempotency-Key` с 428.** Payload пуша
  описывает желаемое состояние целиком, так что повтор идемпотентен по построению.
- **`ETag` / `If-Match` / 412 на операциях черновика.** Черновик и так сериализован
  частичным уникальным индексом, а каждая мутация возвращает пересчитанный поток целиком.
  Требовать заголовок, которого фронт не шлёт, — это 428 на второй же кнопке.
- **Rebase конфликта** проигрыванием журнала операций поверх чужой правки. Остаётся
  обнаружение, 409 и показ расхождения с выбором «перезаписать / отменить».
- **Таблица `keitaro_calls`.** Структурный лог с correlation id отвечает на тот же вопрос
  и не растёт в базе.
- **Отдельный сервис-заглушка Keitaro.** Доступ к живому трекеру был с первого дня, поэтому
  фейк живёт в `tests/` как вторая реализация тех же портов — в том числе в двух вариантах,
  replace и merge, потому что семантика `PUT /streams/{id}` это открытый вопрос. Отдельным
  контейнером он полезен ровно одним: `docker compose up` работал бы вообще без ключей.
  Это первый кандидат на добавление.
- **`OriginCheckMiddleware`.** В том виде, в каком его хочется написать, он отклоняет
  собственные же запросы SPA: браузер шлёт `Origin` и на same-origin POST. Same-origin
  деплой плюс авторизация заголовком, а не куками, закрывают классический CSRF.
- **`alembic check` и `downgrade base && upgrade head` в CI.** Вместо этого схема, против
  которой идут тесты, строится **миграциями** (`alembic upgrade head` перед `pytest`), а не
  `create_all`, плюс два теста на саму цепочку: она линейна — две ревизии с общим
  `down_revision` дают «Multiple head revisions» на чужой машине в момент деплоя — и ни один
  `downgrade` не пустой.
- **Playwright.** Скриншоты и GIF сняты руками один раз; поддерживать браузерный
  прогон ради четырёх картинок дороже, чем они стоят.
- **Тёмная тема.** Эталон светлый, а «грязный» жёлтый фон пришлось бы подбирать заново.
  Наполовину сделанная тёмная тема хуже отсутствующей.
